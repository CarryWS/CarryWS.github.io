修好一个错误码之后，我决定不把它开源

2026-11-12

这周我花了一个晚上，只为了搞明白一个错误码：photoAuthError_PCR007。

它来自某在线教育平台的签到页。页面只告诉我「签到失败」，不告诉我为什么。我去 GitHub 搜过这个字符串，结果是 0 条——没有任何人提过它，没有 issue、没有讨论、没有踩坑记录。

后来的事情有点意外：我确实把它修好了，而且顺手把这个过程做成了一套能跑的东西。但最后我决定不把它开源。这篇写的是过程，也是这个决定。

一、一开始根本不是这个问题

事情的起点跟签到本身关系不大。之前我用某个开源仓库，在自己的服务器上搭了一套签到工具服务——网页版，填好坐标点提交，比跑到教学楼底下方便。那天早上有个位置签到，我照旧从地图软件取了教室的坐标填进那个服务，它回了我一句：距离签到位置约 800 米。

800 米这个数字很奇怪。教学楼确实在那个地方，坐标是从地图上点出来的，不该差这么多（因为之前在楼下签到就没问题，说明平台允许的误差没那么小）。我第一反应是自己点歪了，重取了两次，还是 800 米上下。

然后我意识到问题不在我这边：国内有三套坐标系。GPS 拿到的原始经纬度是 WGS-84，高德腾讯这些用 GCJ-02（也就是「火星坐标」，国家规定的偏移），百度单独用 BD-09（在 GCJ-02 基础上又加了一层偏移）。

我按标准算法手算了一下：

GCJ-02 → BD-09：约 880~914 米
GCJ-02 → WGS-84：约 360~570 米

屏幕上那个 800 米，正好落在 BD-09 那一档。也就是说，平台要的是百度坐标，我给的是高德坐标，两套之间差的就是那八百多米。

这个坑不新鲜，但它的隐蔽之处在于：坐标本身完全合法，格式也对，甚至精度有六位小数——它只是「不是同一个坐标系」。你不会收到任何格式错误，只会收到一句「你离签到点很远」。

二、真正卡住我的是第二个问题

坐标系的问题想明白之后，又打算换一个实现签到的仓库。然而我翻遍了整个 GitHub，发现那种能够用于服务器部署，有前端和后端的签到工具几乎就没了，而且现用的这个也不太好用，所以只能自己动手了。

我另外找了一个能实现签到的仓库，用的是Python实现的，这对于我来说是一个好消息——它很容易就能爆改成一个服务的后端，而前端我随便做（无论是样式还是功能），而我不太喜欢上一个服务恰恰就是因为那个服务的前端做的很粗糙。

做好了之后晚上上课，趁着老师签到顺便测试了一下用这个工具上传图片进行拍照签到的功能。

然后就撞上了那个错误码。

我按流程把照片传到了平台的云盘，拿到文件 id，提交——失败，还是 PCR007。

我当时的反应和你一样：是不是图片没传上去？于是我做了排除：

  • 不带图片提交 → PCR007
  • 带上云盘返回的 resid → PCR007
  • 带上云盘真实列表里那条记录的 objectId → PCR007
  • 换成 POST 表单提交（而不是 GET） → PCR007
  • 把 clientip 填成真实出口 IP → PCR007
  • 把提交端从自己的电脑换成家里那台常开的小主机（出口是国内家庭宽带） → PCR007

六个变量，一个结果。到这里可以确定：不是我这边的问题，不是网络、不是 IP、不是请求方法、也不是「图片没传成功」。

我甚至一度得出了一个错误的结论：「这个签到要求用 App 相机现场拍，服务端拒绝一切外部提交」。这个结论听着很合理，也很有说服力——它就是错的。

三、转折点是一个只用来测试的群

第二天晚上，我跟一个同学说了这事。他说：「那我建个群，发个拍照签到给你测。」

于是有了一个只有两个人的群，名字叫 test，里面躺着两个签到，第二个特意勾了「要求拍照」。

这个群本身没有用途，纯粹是为了让我有一个可以随便失败的样本。事后看，这是整件事里最关键的一步——有一个可复现的、可以随便试错的目标，比在真实签到里猜十次都值。

四、抓包：把黑盒变成白盒

既然排除了外部因素，就只剩一个办法：看它到底发了什么。

我手机插在电脑上，开了 USB 调试，思路是把手机的 HTTPS 流量导到电脑上的 mitmproxy 里解密。中间踩了两个坑：

第一个坑：安卓的输入注入被锁。 我本来想全程用 adb 遥控手机，结果 adb shell input tap 直接被系统拒绝：

java.lang.SecurityException: Injecting input events requires the caller
to have the INJECT_EVENTS permission

国产 ROM 默认把「USB 调试（安全设置）」关着，得去开发者选项里单独开。这个开关不在普通的「USB 调试」旁边，很容易漏。

第二个坑：证书要装在手机里。 mitmproxy 默认只解密它自己信任的流量，手机不装它的根证书，看到的全是加密后的二进制。装证书的顺序也很讲究：先装证书、再开代理。反过来的话，代理一开手机立刻断网，你连设置页面都进不去。

装好之后，群里的每个请求就都能看了。点开那个签到，我看到了这么一串：

GET /sign/preSign?...&activeId=22576364&chatId=330396556394497&uid=...

两个关键 id 直接暴露在 URL 里。紧接着的请求是一个 HTML 页面——签到页不是原生界面，是服务端下发的网页。

这一点很重要。它的意思是：提交逻辑不在 App 的安装包里，而在这个 HTML 的 JS 里。 所以再花几个小时反编译 APK 都是白费力气（我确实先拉了一个 259MB 的安装包，翻了一遍，发现里面只有一个加固壳加一堆无关代码，才想明白这件事）。

五、答案在页面的 JS 里

我把那个页面拉下来，找到提交函数，它长这样：

var PHOTO_RESULT = object ? JSON.stringify(object) : "";
$.ajax({url:"/sign/stuSignajax", type:"post", data:{
  activeId, uid, clientip, useragent, latitude, longitude, fid,
  objectId: objectId,
  photoResult: PHOTO_RESULT
}})

我盯着这行看了很久，然后意识到我一直在做一件蠢事：我提交的时候，根本没有这个字段。

更妙的是它的结构。页面注释里写着，这个 object 是 App 相机回调传回来的，形如：

{"files":"[{\"name\":\"x.jpg\",\"objectid\":\"...\",\"type\":\"jpg\"}]"}

注意那个引号——files 的值是一段字符串，不是数组。因为 App 传回来的 files 本身就已经是 JSON 文本了，页面又对它做了一次 JSON.stringify，于是成了一个「字符串里套 JSON」的两层结构。

如果你只按直觉把它写成 {"files":[{...}]}，服务端依然会拒绝——格式错一层，校验就过不去，而它不会告诉你哪里错了。

补上这个字段之后，同一份请求，返回从 photoAuthError_PCR007 变成了：

success

六、顺带修掉的两个坑

排查过程中还发现，原来那套上传图片的逻辑早就失效了，只是它失败得很安静：

一是云盘页面的结构变了。 旧代码去页面里找一个叫 _rootdir 的变量，而新版页面早就跳转到了 /mobile/fileList，变量也改名了。结果就是：即使你把图片老老实实放在根目录，它也永远找不到。它不报错，只是「找不到图」。

二是上传接口分两个。 老的那个 upload/uploadfile 返回的是 resid，而签到要的是 objectId；能拿到 objectId 的是另一个地址，还得先请求一次 token 接口，而且 token 要从返回的 JSON 里单独取一个字段——直接把整串 JSON 当 token 用，永远拿不到。

这两个加起来，就是「你以为自己在传图，其实系统根本没看见」。

七、插一段：这些活其实大部分不是我干的

写到这里得停一下，说点不太符合「技术博客」惯例的话：上面这些活，大部分不是我干的，是 AI 帮我做的。

我自己的知识储备确实不多。DES 加密、坐标系那套偏移算法、页面里的 JSBridge、Docker 的构建层——这些我基本是从零开始，一边问一边理解的。上一篇写 SSD 故障的时候我还能说「那是我自己排查的」，这一篇不行，得诚实一点。

但有一件事是我主动提出来的：去抓包。

在它给出一堆「可能是要求 App 现场拍照，所以拒绝一切外部提交」的推断之后，我没有继续在参数里瞎猜，我说的是：「能不能直接抓手机的网络，看它到底发了什么？」

理由很简单：我自己用 App 是能签上的。既然 App 能签上，那它一定发了某个东西，而我没发。看它发了什么就知道了。

后来证明这个方向是对的。真正的答案不在任何文档、任何搜索结果里，只在服务端下发的那页 JS 里；不抓包，你永远只能看到「跑不通」三个字。

所以这篇记录的功劳大概可以这么分：技术实现是 AI 的，方向选择里至少「去抓包」这一条是我自己的。

写出来不是为了自谦。我只是觉得，把「一个学生 + 一个 AI」的真实分工讲清楚，比假装什么都会更有用——也许有人看完会想：那我是不是也能提出一个 AI 没想到的方向。

八、然后我开始犹豫

代码跑通的那天晚上，我本来已经在想镜像怎么打了——Dockerfile 都写好了，多阶段构建、非 root 用户、健康检查，跑起来验证过，81MB 的镜像，端口、时区、证书全都能对上。下一步就是推到 GitHub，配个 README，让别人一键部署。

然后我停下来想了一个问题：我真的想让别人用它吗？

我那个帮忙建群测试的同学说了一句话：「这种软件的开发者和我们这类大学生之间，本身就存在一种博弈。」

他说得对。我今天修好了 PCR007，平台明天可以换一个 PCR008；我把云盘的变量名从 _rootdir 改成 rootdir，下一次它可以再改一次。这不是「解决问题」，这是在一个会主动对抗你的系统上做持续维护。

而维护是有代价的，而且代价不对称：

  • 一旦有人开始用，他们签到失败第一个找的人是我
  • 平台一改，我会被当成「工具坏了」的那个人
  • 而我从这件事里得到的，大概就是几十个 star

更现实的一层：这个领域已经有过先例。我在查资料的时候翻到一个仓库，作者在 README 里留了一句话——「收到官方律师函，已删库」。也有另一条路线，一个一千八百多星的同类项目，最后不是被封，是作者自己把它归档了。两种结局，本质上都是「做不下去了」。

我还在读书，这个项目的署名会挂在我自己身上。真到了要处理法律问题或者学校纪律问题的那一步，那几十个 star 一分钱都不值。

九、我的决定

所以我做了三个决定：

  • 不发可运行的工具。镜像我不推公共仓库了，Dockerfile 也就留在自己机器上。
  • 写这篇笔记。因为这次真正值钱的东西不是那个脚本，而是排查的方法。
  • 把项目里的个人痕迹清干净。我在准备发布前扫了一遍，发现 compose.yml 里有我的内网地址、Dockerfile 注释里有我的用户名、数据库文件里有手机号和明文密码。这些东西只要进过一次仓库，就永远在别人的 fork 里了——这一点大概是所有第一次开源的人都该先知道的。

十、留下来的东西

工具我没发，但方法可以留下。这几条是我这次真正学到的，跟具体平台无关：

  • 错误码是最好的线索，但要先确认它是不是新的。 搜不到，往往意味着「刚上线」而不是「没人遇到」。这种时候排除法比搜索有用。
  • 一次改一个变量。 我一开始同时怀疑了图片、网络、IP、请求方法，结果每一步都是凭感觉。后来列成一张表逐个排除，反而快。
  • 先判断逻辑在哪一层。 我差点花一晚上反编译一个加固过的 APK，而真正的提交逻辑写在服务端下发的网页里。一个页面和一个安装包的体积差了几百倍，信息密度却反过来了。
  • 找一个可以随便失败的样本。 那个只有两个人的测试群，比我前面所有猜测加起来都有用。
  • 「格式错一层」是最难查的 bug。 缺字段、多一层嵌套、类型从数组变成字符串——服务端通常只会给你一个笼统的失败码。这时候唯一能做的就是去看它原本怎么发的。
  • 开源之前先想清楚自己在承诺什么。 开源等于承诺维护，而有些东西的维护成本会随着使用者增加而上升，收益却不会。

最后说个有点微妙的感受。整件事里最让我高兴的，不是最后看到那个 success，而是盯着那行 JSON.stringify 想明白「哦，原来它是两层」的那几秒。那种感觉跟打游戏通关不一样，它更像是在一个别人设计好的黑盒里，找到了一条真实存在的缝。

只是找到缝之后，我选择不再往里走。
